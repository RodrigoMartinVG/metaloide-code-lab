paso 3 de 5 · ¿Qué pasa cuando asignamos?

Tenés una String en s1. Escribís let s2 = s1. ¿Qué pasa exactamente?
Compilá y observá el error. Después mirá la visualización de memoria a la derecha.

1fn main() {
2 let s1 = String::from("hello");
3 let s2 = s1; // move occurs here
4
5 println!("{}", s1); // E0382
6}
¿POR QUÉ EL ERROR?

String no implementa Copy. Cuando escribís let s2 = s1, la cadena pasa a ser propiedad de s2 — s1 queda inválido. Rust no permite tener dos variables que se crean dueñas del mismo heap.

Esto evita el double free: si ambas variables existieran al salir del scope, las dos intentarían liberar la misma memoria.

El gran descubrimiento

Rust hace algo que ningún lenguaje mainstream hace: transfiere la propiedad de los datos en lugar de copiarlos o referenciarlos por defecto. Esa decisión cambia lo que el compilador puede garantizar — y lo que puede rechazar.

§ 4.1

El código que rompe

Antes de ver qué hace Rust, hay que ver qué rompe. El programa más simple para demostrar ownership no hace nada misterioso: crea una String, la asigna a otra variable, y trata de usar la primera.

El compilador lo rechaza. ¿Por qué? La respuesta está en lo que String representa en memoria — no un valor, sino una promesa de liberación.

src/main.rs
fn main() { let s1 = String::from("forja"); let s2 = s1; println!("{}", s1); }

§ 4.2

La memoria, observada

Una String en el stack es tres palabras: un puntero al heap, una longitud, y una capacidad. Lo que se mueve cuando escribís let s2 = s1 no son los bytes del string — son esas tres palabras del stack. El heap no se toca.

Rust invalida s1 en el compilador. No en runtime. No hay instrucción extra — solo una regla que el compilador aplica sobre el grafo de flujo de control.

§ 4.3

El error, en sus palabras

El mensaje de error de Rust es inusualmente preciso. No dice "variable no existe". Dice exactamente qué pasó — en qué línea ocurrió el move, dónde intentaste usar el valor movido, y qué podés hacer.

Leer los errores del compilador de Rust es una habilidad separada. E0382 es el primero que todos encuentran, y es el mejor diseñado: la causa, la consecuencia, y la sugerencia están en el mismo mensaje.

E
E0382 — "borrow of moved value". La solución sugerida (s1.clone()) es válida cuando necesitás dos copias independientes. Pero clonar tiene costo: copia todos los bytes del heap. Avanzá al paso 3 para ver la alternativa sin costo: el borrow.
"Rust no te impide hacer cosas peligrosas porque no confía en vos. Te las impide porque encontró una forma de garantizar seguridad sin ningún costo en runtime."
— Programming Rust, Blandy · Orendorff · Tindall
¿
¿Por qué así?
¿Por qué Rust eligió mover la propiedad en lugar de copiar implícitamente, usar reference counting, o garbage collection? ¿Qué haría cada alternativa en un contexto de sistema — en términos de seguridad, performance, y lo que el compilador puede y no puede verificar?
No hay respuesta correcta. Tu razonamiento queda guardado y va a aparecer la próxima vez que pases por aquí.
